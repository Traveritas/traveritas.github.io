# 星 · 平滑程度（design/mocks/star-t-smooth）

> 2026-11-10 ｜ 端口 **4668** ｜ 只回答一件事：同一颗三轴正交六芒星，棱角磨到什么程度最好看。

结构定了 —— `±x ±y ±z` 六支，停在 yaw 45° / pitch 35.264°（唯一投影成正六芒星的那一格）。
这一轮不动形状家族，只动五个互相独立的「平滑」旋钮，然后把它们合成四档完成度摆在 200 与 400 上比。

node design/mocks/star-t-smooth/.light3.mjs      # 光向扫描（101 行输出，见 §2）

## 0. 一句话结论

> **真正决定「像不像一块晶体」的只有两项：脊（折高）与明暗跨度。**
> 尖端、棱上圆角、截面边数这三项，在 200px 上全都属于「有官能差别、无观感差别」——
> 它们只在 400px、而且只在中心与尖端那两处放大的时候才读得出来。
> **中心那堆碎条不是「中心没做好」，而是「支尾太尖」的后果**；给支尾一点宽度、再压一块有方向的顶，
> 它就变成六条支收在一处，而不是十几个互不相干的小三角。

推荐两档（path 数一并给出，见 §5）：

| | 预设 | path | 片 | 调子档 | 一句话 |
|---|---|---|---|---|---|
| 大尺寸（200–400px）、要「晶体」 | **锐利晶体** `crisp` | **25** | 92 | 6 | 八边 + 五档 + 硬尖，角都留着 |
| **推荐默认**、任何尺寸 | **磨砂** `frost` | **24** | 82 | 5 | 六边 + 四档 + 小圆角 + 尖削平一线 |
| 最省、最软 | **柔钝** `soft` | **19** | 157 | 4 | 四边 + 三档 + 大圆角 + 尖收圆 |
| 看上限 | **极致** `max` | **32** | 248 | 6 | 八边 + 五档 + 大圆角 + 圆尖 |

现役 `drawStar()` 是 **7 path**、2 档、支内落差 0。所以最省的「柔钝」也是它的 2.7 倍路径数；
真正落进工具栏那种每帧重画的地方，代价要按这个倍数算，不是按「反正才二十几条」算。

## 1. 几何做法（与 star-solid 的 ridge 不同）

每支有一组正交基 `{a, side, ed}`：

- `a` 支的单位方向（视空间）
- `side` 屏幕上与支垂直的方向（就在屏幕平面里）
- `ed` 与 `a` 垂直、且尽量朝观者的方向 = `(k − ẑ·a) / |…|`

截面就摆在这张 `(side, ed)` 平面上 —— **是真横截面，不是一条侧着的窄条**。
截面沿轴等比缩到端点（`W(s) = w·(1 − s/r)`），每一片是三角形或四边形，
法线由 Newell 法从真顶点算。

### 两处对旧 ridge 的修正

1. **旧 ridge 的「轮廓一个像素不改」其实不成立。** 它抬肩用的是 `cross(a, side)`，
   那个方向在屏幕上有分量，肩沿支方向滑开 `0.58·h`。这一版用真横截面，
   轮廓不变是几何上成立的 —— 截面深度只把顶点推向风筝内部，推不出轮廓。
2. **旧 ridge 靠 `0.7·shade + 0.3·depth` 硬混出明暗。** 这一版法线来自真顶点，
   深度混入默认只有 0.22；把它调到 0 也还能看（`.probe` 里试过），只是远支会跳出来抢。

### 不变量

- 投影轮廓仍是现役那张四角风筝：端点半径 13.06（`r·√(2/3)`）、半宽 1.9、支尾 1.7 全部沿用。
- 凹口半径 **3.0354** 用户单位。star-solid 的 notes 里写的 `w·cosα/sin(60°−α) = 2.8135`
  是**错的**：相邻两支的刃并不在原点附近相交，而是在更外面才擦肩。正确的算法是
  一支的侧角点 `(w·sinθ, w·cosθ)` 连到端点那条刃，与相邻支的对称轴求交 —— 量出来 3.04。
  48px 取景框下这个凹口是 **4.8px**（不是旧 notes 里那个按 2.8135 算出的数）。
- 正等轴视角下六支投影等长、互成 60°，所以凹口每处半径相同。

## 2. 光向：这一轮的意外发现，也是唯一改了基线以外东西的一处

**光不能只在屏幕平面里。**

六支的两肩（截面的 `side` 方向）在屏幕上落在 0° / 60° / 120° 三个方位（正反各一，
所以是 0/60/120/180/240/300 这六个方向的 ±）。若光也在屏幕平面里，它总与其中某一对 `side`
平行或近似平行，那一对支的左右两肩就同色 —— **那两支整支没有折，调子白算**。

第一条我试的方向是「屏幕正上」（`[0, 1, 0.02]`）：竖直那两支退成一整片，其余四支全是死黑。
第二条是「左上前」（`[-0.34, 0.52, 0.79]`，也就是 star-solid 的默认）：好一些，但六支的
明暗序有 4 对重复（`sameOrder = 4`），看过去像被斜着打了一束光。

### 扫法

方位 0–355°、仰角 −40–70°，各 5° 一格（**2160 格**），三个判据：

| 判据 | 意思 | 取 |
|---|---|---|
| `spineRaw` 取最小 | 六支里**最差**的那支也要有支内落差 | 越大越好 |
| `notch` 取最小 | 相邻两支在凹口两侧也要有落差 | 越大越好 |
| `sameOrder` | 相邻两支明暗序相同的对数 | 越小越好（0 = 六对全相反） |

用「最小」而不是「平均」，是因为**一颗星里只要有一支是平的，整颗就塌**。
这也是为什么第一版的平均分看着不差、看上去却不对。

### 结果

`az 30° / el 25°` 与它的镜像 `az 150° / el 25°` 在 ①② 上同时最高：

```
az 30 el 25   spineRaw 最小 0.44   notch 最小 0.49   sameOrder 2
az 90 el 30   spineRaw 最小 0.37   notch 最小 0.00   sameOrder 2    ← 之前用的，交界处有同色接同色
az 90 el 0    spineRaw 最小 0.49   notch 最小 0.00   sameOrder 6    ← 纯屏幕光，六对全同序，死板
```

固定为 `LIGHT = normalize([0.78, 0.42, 0.45])`。

**这条不在简报的五个旋钮里，但它先于五个旋钮。** 光向不对，五个旋钮怎么扫都扫不出差别 ——
我第一次扫折高时 `fold 0.25 / 0.5 / 0.75` 三档的读数全是同一个数，就是因为光向让那几支一直是平的。

## 3. 五个旋钮：哪个有用，哪个只是官能

### ① 尖端 —— 官能，不是观感

| 做法 | 退让 | 200px 上看得出来？ |
|---|---|---|
| 硬尖 `cusp` | 0 | — |
| 削平 0.6 | 0.6 | **不**（0.4px） |
| 削平 1.4 | 1.4 | 勉强 |
| 削平 2.8 | 2.8 | 看得出来 |
| 收圆 ρ0.06 | 0.4 | **不** |
| 收圆 ρ0.12 | 0.9 | 勉强 |
| 收圆 ρ0.2 | 1.5 | 看得出来 |
| 收圆 ρ0.42 | 3.1 | 明显，但尖已经短了一截 |

**收圆的退让是半径的 7.5 倍**，这是解出来的不是调的：圆弧要与两侧刃相切，
半张角 `α = atan(1.9/16) = 6.77°`，退让 `= ρ·(1/sin α − 1) = ρ·7.48`。
所以「细长的尖要圆」这件事本身矛盾：圆到看得出来，长度就保不住。

**结论：这一项只在 400px 上值得调。** 200px 及以下用硬尖或削平 0.6，看不出区别，还省 path。

### ② 脊 —— **最要紧的一项**

`fold` = 截面脊高 ÷ 半宽。`0` 就是现役那张平风筝。

| fold | 最小支内落差（量化前） | path |
|---|---|---|
| 0 | 0.00 | 7 |
| 0.25 | 0.11 | 12 |
| 0.5 | 0.21 | 17 |
| 0.75 | 0.32 | 19 |
| **1.0** | **0.39** | **21** |
| 1.2 | 0.44 | 21 |
| **1.5** | **0.49** | **22** |
| 1.8 | 0.53 | 22 |
| 2.2 | 0.57 | 21 |

- **0.5 起才真的看得见**；0.75–1.5 是甜区；1.5 之后每格只多挣 0.04，不值。
- 1.8 起六支的刃开始互相压，剪影的凹口被吃一口；2.2 已经不是「一支折过」了。
- 这仍然是 star-solid 那条结论的复现与修正：它说「唯一读成晶体」，对；它没说 fold 的甜区，
  §6 里也承认「没做参数扫描」—— 这里补上了。

### ③ 棱上圆角 —— 有，但排在很后面

做法：把 `±(1, 0)` 这两个角换成一段内切圆弧（半径 `fillet`，在 `(nu, de)` 参数平面上取）。
**轮廓一点不变**（±1 那个点还在），只是那个角被切成两小段，于是边上多一条自己的调子。

| fillet | path | 片 |
|---|---|---|
| 0 | 21 | 43 |
| 0.06 | 23 | 91 |
| 0.12–0.24 | 23 | 91 |

**片数翻一倍，path 只多两条** —— 圆角那两小片与邻近的片同色，并掉了。所以它「贵」在片不在 path。

第一版我把这条带做成「边缘回沉」（刃往内让一截），轮廓真的变窄了，六支立刻发虚。
现在这版是内切的，剪影一个像素没动。**这是这一轮唯一一次「看着不对 → 找到是几何错」。**

观感上它让边不那么死，但比不上折高那一项的一个零头。

### ④ 截面边数 —— 200px 上看不出，400px 上读得出

四边 → 正面两片；六边 → 三片；八边 → 四片。

| 边数 | 片 | path | 脊上是什么 |
|---|---|---|---|
| 4 | 25 | **16** | 一道折线，明暗一分为二，最利 |
| 6（圆角 .12） | 79 | **22** | **一条平面**，整条一起亮，折的感觉反而没了 |
| 8（圆角 .12） | 91 | **23** | 一道折 + 两侧各一道台阶 → 明—次明—暗三段 |

（三档都取 `fold 1.2`、五档 0.10–0.94，六边与八边带棱上圆角 0.12 —— 同条件才可比。）

**这里得说一句与直觉相反的话：更多边不等于更像晶体。** 六边在脊上做成平面，
反而把「折」这个信息抹掉了 —— 它是这一列里最平的一档。四边最锐，八边最有体积，
六边夹在中间两头不靠。

`200px` 上四边与八边的差距，比五档与四档的差距还小；放大到中心与尖端才分得开。
**贵，而且是这一页最贵的一项。** 除非要 400px 的主视觉，用四边更划算。

### ⑤ 明暗 —— 第二要紧

把连续明暗量化成 `steps` 档，再乘到 `min–max` 的跨度上。

| | 读感 |
|---|---|
| 2 档 0.486 / 0.774（现役） | 它在为「远与近」服务，不是在为「面与面」服务 —— 同一个数既管远的支又管暗的面。中间 0.288 的跳空撑不起体积 |
| 2 档 0.12–0.92（拉宽） | 像两块板，反而硬 |
| **3 档** | 够立住 |
| **4 档** | 最稳 |
| 5 档 | 200px 上与四档无从分辨；只在 400px 上多一点点空气 |

跨度同样是参数：0.24–0.80 发灰，0.05–0.97 发花（最亮那片与底色撞上）。**0.10–0.92 是平衡点。**

### 一条附带的坑：量化会把折吃掉

四边 + 四档时，有一支的两侧刚好被切进同一档，支内落差从 0.15 直接变成 **0** —— 那支就是一整片。
**档数要给得比「看起来够用」多一档。** 八边 + 四档时最小落差 0.42，是安全的；
四边 + 四档是这一页唯一一处「参数看着没问题、结果一支塌了」的地方。

读数页里「最小支内落差」一律报**量化前**的那个值（`spineRaw`），因为量化后的值会跳台阶，
拿它当尺子会得出「fold 从 1.0 加到 2.2 毫无变化」这种假结论 —— 我第一版就是这么报的。

### 归一化

档是**先归一化再乘跨度**的：先把整颗星的 `t` 拉到 `[0, 1]`，再量化。不归一化的话，
六个调子会全挤在亮的一头（因为面上的 `dot(n, light)` 大多在 0.5–0.9 之间）。

## 4. 中心：碎条真正的成因

作者说薄版的中心是「一堆没有意义的交叉碎条」。查下来，**它不是中心缺东西，而是支尾太尖**：

- 现役支尾是**越到末端越窄的尖**（`W: 1.9 → 0`，长度 1.7）。
- 六条支尾在中心附近都只剩一两个像素宽，六条窄片叠在一起，交出来的就是十几个小三角，
  **每一个都不属于任何一条支** —— 所以「没有意义」。
- 板子一厚（`fold` 上去），端点就有宽度，那些小三角变成看得懂的小面。

三档做法：

| | 做法 | 判断 |
|---|---|---|
| `none` | 什么都不放 | 薄版就是这样，碎条最明显 |
| **`table`** | 一小块朝观者的六边形，有面、有方向 | 能用；最稳 |
| **`split`** | 同一块沿光的垂直方向分两半，一明一暗 | 最好 —— 与六支的明暗结构接得上 |
| `pale` | 几乎与底色同值，只当一层底 | 也能用，但与六支脱钩，像盖上去的 |

**这是这一页里唯一「按简报的描述找到了真因」的一项。** 简报说「加块东西盖住」，
实际是「支尾本身要改」—— 中心那块的形状是次要的，它的调子要与周围接得上才是主要的。

## 5. path 数与代价

**片数涨得快，path 数涨得慢** —— 因为同一支上同色的片会并成一条 path（这时几何不变，
只是少几个节点）。所以真正该报的是 path 数：

| | path | 片 | 相对现役 |
|---|---|---|---|
| 现役 `drawStar()` | **7** | 7 | 1.0× |
| 四边 · 硬棱 · 4 档 | 15 | 25 | 2.1× |
| 六边 · 小圆角 · 4 档 | 21 | 79 | 3.0× |
| 八边 · 小圆角 · 5 档 | 23 | 91 | 3.3× |
| **锐利晶体** `crisp` | **25** | 92 | 3.6× |
| **磨砂** `frost` | **24** | 82 | 3.4× |
| **柔钝** `soft` | **19** | 157 | 2.7× |
| **极致** `max` | **32** | 248 | 4.6× |

现役 `drawStar()` 每帧写 6 条 + 一个心，`design/mocks/star-crystal/notes.md` §5 与
`design/mocks/star-solid/notes.md` §4 都算过这个账：这一站对空闲帧很计较。
**所以「用哪一档」不只是审美问题：最省的柔钝也是 2.7 倍。**

注意 `soft` 的片数（157）比 `crisp`（92）还多，path 反而少 6 条 —— 因为它只有三档，
且四边的片本来就少，同色并得掉。**别拿片数当代价指标。**

## 6. 尺寸

| 尺寸 | 凹口 | 判断 |
|---|---|---|
| 48px | 4.8px | **只有「锐利」还站着**。柔钝因为大圆角，整支的边宽被吃掉一角，六支之间的空隙进一步收窄，已经读成一团 |
| 96px | 9.6px | 四档的差别第一次变得可辨 —— 但也只是「可辨」，不是「可选」 |
| 200px | 20.1px | 真正能拿来比的尺寸 |
| 400px | 40.2px | 尖端与棱上圆角的差别在这里才值得调 |

要落进 40px 的工具栏钮，这一套里只有锐利勉强，**而现役那张平风筝在 48px 上其实更干净** ——
它在那个尺寸上并不缺「厚度」，只缺清晰。

## 7. 没做到的 / 与预期不符的

1. **光向这一条不在任务里。** 简报让我扫五个旋钮，我花了一多半时间在定光向 ——
   因为不定它，五个旋钮全是假读数（见 §2）。这算越界，但不定它这页没法交。

2. **四边与八边的差别，我说不出「哪个更好看」。** 我能确定的是「八边有三段、四边有两段」，
   以及「200px 上两者差距极小」。选八边是因为它更接近「晶体」这个词，不是因为我量出了它更好。

3. **`fold 2.2` 那两格不该留在扫旋钮里。** 它是坏的（六支的刃互相压），
   留着只为说明「过头了会怎样」。但我也没验「压到哪种程度算真的坏」—— 这条线是估的。

4. **收圆的几何是对的，观感不一定好。** `ρ 0.42` 那一档（退 3.1）看起来像一支被啃过头的蜡笔，
   不是「磨圆的尖」。要让圆尖真正好用，得允许尖端不保持圆——那就是椭圆收口，这一轮没做。

5. **「档数会把折吃掉」这条我是撞上才发现的，没做系统验。** 我只知道四边 + 四档会塌一支，
   八边 + 四档安全。每档组合的最小落差没有逐一列出 —— 表里只给了我实际用到的几组。

6. **所有判断都在一个光源下做出。** 换成两个光源（主光 + 补光）时，§2 那三个判据的最优解会变；
   我只在 `.light2.mjs` 里粗算过一次「补光方向」的搜索，没有真接进去试渲染。

7. **没验 `prefers-reduced-motion`。** 这一页是静帧，本来不涉及；但真要接进站点，
   旋转与定格的那一套（star-v-motion 的结论）与这里没有接起来试过。

8. **白色 / 深底以外的底色没试。** 站点还有梦面那套（`--umber #4f4a66` 一系），
   这一页只摆了 `#f0f3f6` 与 `#2a2b38` 两个。梦面底色上的观感可能完全不同 —— 尤其「退淡」那个中心。

9. **`soft` 的片数 157 是我没料到的。** 四边 + 大圆角时每支的圆角要把轮廓切成四段，
   片数反而比八边多。path 数救回来了，但「柔钝最省」这句话只对 path 成立，对片数不成立。

10. **中心那三档做法的名字是我临时起的**（平顶/劈开/退淡）。真落地时这三个应该跟着
    「这一页在讲什么」重命名，不是跟着几何命名。

### 自检

页面暴露 `window.__readout`（光向、凹口半径、四档的 path/片/调子、每次扫的读数）、
`window.__sections`（每段高度）、`window.__sec`（截面对照的 path 数）、`window.__ready`。
`.shot.cjs` 读前两个；`__ready` 为 true 才截图。
