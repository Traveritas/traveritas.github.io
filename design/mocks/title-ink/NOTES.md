# 标题取色 · 对照原型

> 2026-10-18。这一轮不做什么新功能，只回答一个问题：
> **那片会漂的流光上，除了「字随底换墨」，还有哪些让字读得清的做法，各自会在什么时候失效。**

## 运行

```bash
node design/mocks/title-ink/serve.cjs      # http://localhost:4644/title-ink/
node design/mocks/title-ink/.shot.cjs      # 截图 → .shots/（ONLY=board-a,board-b,board-c,mobile）
```

静态、无构建、无依赖。字体从仓库现取（`/fonts/noto/`、`/fonts/plex/`），不联网。

## 三块板

| | 底 | 为什么 |
| --- | --- | --- |
| `#board-a` | 标定夜色带 | 色值取自 `src/scripts/wander/light.js` 的 DREAM 调色板：暗靛 → 随笔池（近白）→ 瞬间池（琥珀）→ 项目池（青）→ 主页池（淡粉紫）。**一维、对每一行完全相同**，所以比较成立；每行的字都横穿全部四种池 |
| `#board-b` | 黑 → 白全亮度带 | 把每种做法的失明点直接摊开，下面有刻度 |
| `#board-c` | 真实一帧 | 从跑着的主页上抓下来的流光画布（`assets/field-frame.png`，288×180 放大）。底会漂，所以这只是一个样本 |

十种做法各占一行，**同一串字、同一个字号，只有取色方式不同**。
`字随底换墨` 那一行不是凭印象画的：它与 A 板的背景出自 `pools.js` 里同一个函数，
C 板上则按那一帧的真实像素取亮度。

截图：`01-board-a-field.png` · `02-board-b-ramp.png` · `03-board-c-frame.png` · `04-mobile.png`

## 各行的结果（B 板黑→白，从左到右）

| 做法 | 在哪儿断 |
| --- | --- |
| 字随底换墨（基线） | 不断。在通道 ≈47%（底 L≈0.19）处**跳**过去 |
| 差集 · 近白墨 | 通道 50% 附近淡掉（底 L≈0.22 处算出来与底同色） |
| 差集 · 琥珀墨 | 同上；色相整个翻成补色（琥珀池上出深蓝，青池上出暗橙） |
| 排除 · 近白墨 | 同上，但整体更闷、对比更低 |
| 滤色 · 近白墨 | **纯白处消失**（左边大半截是好的） |
| 正片叠底 · 深墨 | **纯黑处消失**（右边是好的） |
| 反相窗 | 通道 50% 附近淡掉；其余地方是「底色的负片」，色相保留 |
| 推色窗 | 通道 50% 与两端**都**淡掉（`contrast()` 把两端推到截断，中间不动） |
| 差集 + 一圈柔晕 | 不断。差集失效的那一段由底下那份固定的暗晕兜住 |
| 单一琥珀墨 + 柔晕 | 不断。底在字背后让路 |

A 板与 C 板上的读数一致：`滤色` 在近白的随笔池上整段消失，`正片叠底` 在暗靛的缝隙里消失，
`推色窗` 在白池与暗处都淡，其余照上表。

## 结论

1. **任何一种单向的混色或滤镜都是底色的单调函数**，所以必然存在一个底色让它算出来与底相同。
   差集 / 排除 / 反相 / 推对比都在通道 50%（线性亮度只有 0.22，肉眼觉得是中灰、算出来并不在中间），
   滤色在纯白，正片叠底在纯黑。这不是参数没调好，是这一类做法的固有边界。
2. **换墨之所以不失效，靠的不是算法更聪明，而是它在分界处跳过去。**
   它的分界（底 L≈0.19 ≈ 通道 47%）几乎正压在差集的失明点上——这两个数本来就同源：
   都是「两墨对底色的对比度相等」那一点。所以「换墨」和「差集」是同一个问题的两种答法：
   一个在临界处跳，一个在临界处塌。
3. **要在纯 CSS 里同时拿到「不断」和「有颜色」，只有两条路：**
   - 差集 + 一圈固定的柔晕（晕只在差集失效的地方露出来）；
   - 单一墨 + 柔晕（放弃让字随底变色，让底在字背后让路）。
   两条都不是纯混色，都借了一点「局部压暗」——也就是说，都让底在字背后让了一点路。
4. **A 板上最贴这个世界观的两行是 `反相窗` 与 `差集 · 琥珀墨`。**
   前者是「底色的负片，色相留着」——琥珀池里的字是暖的暗、青池里是冷的亮，像字本来就长在池子里；
   后者颜色最烈，但色相是被底决定的、不由你选。要哪一种，得人眼定。

## 实现上的坑（都实测过）

1. **Chrome 不会把 `backdrop-filter` 的结果交给本元素的 `mask`。** 先按直觉写成
   `backdrop-filter: invert(1); mask-image: <字>`，结果得到的是一整块矩形（截图里能看回改之前那一版）。
   所以「字是底的一扇窗」不能这么做，只能拿**底的第二份拷贝**加滤镜再按字遮罩——
   在原型里底是渐变所以随便拷，落到正站上就是「同一片流光画第二遍」。
   顺带：把 mask 挂到 backdrop-filter 元素的**祖先**上也不行，那会切断它能看到的那层背板
   （`design/mocks/wander/NOTES.md` 第 1 条坑）。
2. **PNG 遮罩走的是 alpha 通道，不是亮度。** 画遮罩的 canvas 底必须留空，只画白色的字；
   填成不透明黑的话遮罩整片不透明，等于没遮。
3. **`mix-blend-mode` 要求祖先链上没有会建层叠上下文的属性**（`transform` / `opacity < 1` / `filter` /
   `z-index` / `isolation`），否则混合被关进那个小组里，混不到板子的底上。行与板都刻意保持干净。
4. `text-shadow` 挂在同一个元素上时**也会被一起混合**，所以「差集 + 柔晕」必须是两个元素。
5. 遮罩用 canvas 画而不是 SVG 里的 `<text>`：字体与排版由同一个浏览器算，不会与 HTML 那一行错位。
   基线按 `fontBoundingBoxAscent/Descent` 与半行距算，与单行块的排法一致。

## 我拿不准、需要人眼确认的

- **`差集 + 柔晕` 的字看着有一点浮雕感**（晕在字的两侧都露出来）。在这块板上读得清、也不难看，
  但放大到主页那个 106px 的字上是什么感觉，我没法判断。`03-board-c-frame.png` 里能看个大概。
- **`差集 · 琥珀墨` 的颜色好不好看**，纯属口味：它在暗处是金、在白池上是深蓝、在青池上是暗橙。
  我不认为这是「错」的，但也不是我会替站长决定的事。
- 三块板里 C 板只是一帧。真要判断观感，得在跑着的主页上把某一行真的挂上去看它随池子漂一遍。
- 移动端（`04-mobile.png`，390×844）只是不溢出、不压字；这个尺寸上池子被压得很窄，
  比较仍然成立但不好看。

## 反相窗：落到正站上的做法与实测开销（2026-10-18 晚补）

在跑着的主页上挂了一版原型（只注入，没动 `src/`），量了一组对照。

### 做法

1. 一个 `div` 贴在标题的矩形上，里面一张 canvas。
2. 每帧从 `#w-light` 上**只拷标题那一小块**：`#w-light` 是 1/5 分辨率（1440×900 下 349×218），
   标题那块在它上面只有 **127×27 像素**。`drawImage` 一次，放大回标题框，`image-rendering: pixelated` 与流光一致。
3. 那个 div 上挂 `filter: invert(1) hue-rotate(180deg)` 与字形的 `mask-image`。
4. 标题自己 `color: transparent`，文本留着当遮罩的来源与给读屏/无脚本的那一份。

### 实测（Chromium 146，逻辑视口 1440×900，DPR 1）

| | 每帧 | 说明 |
| --- | --- | --- |
| 现状（取墨在跑） | 16.7 ms · 59.9 fps · p95 16.8 | 六段测量全部同一读数 |
| 现状 + 反相窗 | 16.7 ms · 59.9 fps · p95 16.8 | **一帧都没掉** |
| 反相窗自身的每帧开销 | **0.20 ms** | 145 帧共 29 ms：4 个样式写入 + 一次 127×27 的 drawImage |
| 建层（一次性） | 0.10 ms | 建 div + canvas |
| 遮罩重生成 | **6.9 ms / 次** | 只在字的文本变化时发生；梦态每 1–2 秒一次，醒态不会 |
| 对照：取墨的读回 | 2.85 ms / 次 ≈ **0.71 ms/帧** | 每 4 帧 drawImage + getImageData(349×218) |
| 对照：取墨的样式写入 | 0.93 ms / 次 ≈ **0.23 ms/帧** | 每 4 帧写 14 条会变的渐变（还额外逼了一次布局刷新，是上限） |

**所以反相窗 ≈ 0.2 ms/帧，被它替掉的取墨 ≈ 0.9 ms/帧 以上，换掉是净赚。**
省下来的主要不是画，是 `getImageData` —— 那是 GPU→CPU 的同步读回，整条管线里最容易卡的一步。

### 便宜在哪

拷贝只有标题那么大。反面做法是把滤镜挂到一份**整屏**的流光拷贝上：那要每帧过滤一两百万像素
（DPR 2 上是四到八百万），而且会逼出一个每帧都要重新过滤的全屏合成层。**别那么做。**

### 坑（都踩过）

1. `mask-size: 100% 100%` 必须写。漏了会按遮罩图片的原始像素铺，只露左上角一块。
2. 遮罩要跟着换面走：梦态下字在 7 个词里轮转，文本一变遮罩就得换。6.9 ms/次落在一帧 16.7 ms 里
   占了三分之一，弱机器上可能掉一帧 —— **把这 7 个词的遮罩起步时预生成缓存**就没了。
3. 标题随滚动会飞成左上角小字，每帧要从它的 rect 重贴位置，飞出画面时把层 `display: none`。
4. PNG 遮罩走 alpha 通道（不是亮度）；遮罩画布按标题框的 DPR 2 出图，边缘才干净。

### 观感与代价

亮池上是池子同色的暗字，暗处是池子同色的亮字 —— 字读起来像「池子自己的一道暗影 / 亮影」，
不是贴上去的标签。池子边缘那一段会淡过去（所有单向做法在通道 50%、线性亮度约 0.22 处的共同死穴），
但实际是一段柔和的过渡，不像换墨那样在字中间劈一刀。
代价是它让「底在字背后让了一点路」，与光流着色器里「字不靠池子让路」那条初衷相反；
要彻底不断，还得再叠一层固定柔晕兜住（见 `差集 + 一圈柔晕` 那一行）。

## 这一轮没做的

- 没有改 `src/` 下任何文件，也没有提交。这只是一块对照板，方向由站长看完图再定。
- 没做「字变成底的一扇窗」在真实 WebGL 底上的版本（那需要在着色器里画第二遍，不是 CSS 的事）。
- 没试 `overlay` / `hard-light` / `soft-light` / `luminosity` 这几个混色：
  按同一套推理它们各自也有失明点（`overlay` 与 `hard-light` 以中灰为不动点），
  放进来只是多几行同类的断，不增加信息。
