## 1 · 那件东西与那个动词

**空间里比内容的窗薄一档的一层窗；动词是打开 / 收起。**

工具不是面板，是**九扇特别小的窗**，和内容的窗漂在同一片空间里。每一件工具就是一扇窗——检索是一扇**能打字的窗**，环境声是一扇**有弦的窗**，目录是一扇**列条目的窗**，换面是一扇**有闩的窗**。

- **收起**：这扇窗只剩一条**窗沿**与**标题栏的一角**（`clip-path` 把它裁到左上 76 × 24 的一小块），贴在屏幕左边缘，一摞九条。
- **打开**：指针靠近左边缘（< 170px），这一摞从边上漫出来，九条窗沿都读得出名字；点某一条，那扇窗自己长开——是**窗本身在开**，不是面板跳出来。
- 一个窗里不重复写名字：**窗沿就是它的标题栏**（空心小圈 · 中文名 · 英文 · 右上角一个开合小角）。

### 薄一档是这一案唯一的立身之本

两档玻璃的差别写在 CSS 的四个数上（`--g-alpha` / `--g-blur` / `--g-edge-a` / `--g-shadow`，加一个圆角），截图脚本每次跑都会把两档的实测值打出来并逐条断言：

| | 底（alpha） | 磨砂（backdrop blur） | 边（edge alpha） | 圆角 | 投影（最大位移） |
| --- | --- | --- | --- | --- | --- |
| **内容的窗** `.c-win` | 0.62 | 16px | 0.26 | 3px | 62px |
| **工具的窗** `.t-win` | 0.34 | 7px | 0.18 | 2px | 18px |

再加两处只有薄玻璃才有的形制：工具窗的标题栏下压一道**上亮下暗的发丝「窗沿」**（`.t-win > .t-sill::after`），内容的窗是 30px 的整条标题栏 + 发丝线。所以同框时看三处就够：**影、边、字后面的东西糊不糊**。

自检里这一条是硬断言（`.shot.cjs`）：`0.34 < 0.62` · `7px < 16px` · `0.18 < 0.26` · `18px < 62px` · `2px < 3px`，并且对照帧里两扇窗**真的相压在同一块底上**。

## 3 · 三条召唤路径怎么走（都落到同一个面）

「同一个面」= 那一摞九扇薄玻璃窗，`dock=0`。自检里 `__t.face()` 逐条比对过：

| | 怎么走 | 唤出什么 |
| --- | --- | --- |
| 一 · **常驻边缘露头** | 什么都不做：左边缘留着一摞**半开的窗**，每扇只剩窗沿与标题栏的一角（`clip-path: inset(0 calc(100% - 76px) calc(100% - 24px) 0)`，实测拿到）。**指针进到离左边缘 170px 以内**，这一摞从边上漫出来，同时把当前语境那一扇打开 | `dock=0`，`open=[find]`（主页 / 检索 / 失线），阅读页是 `[toc]` |
| 二 · **指针跟随 / 拖拽** | 指针靠近后按住某扇窗的**窗沿**往右拖——窗就跟着指针走，松手落在指针放下的地方（`localStorage['xm-tw-free']` 记着 x / y，**再打开也还在那儿**）。窗沿右侧的「—」把它**收成一枚纸签**（104 × 22，只剩名字），点纸签再展开。`Esc` / `W` 收起时只把打开的那一扇合上、把这一摞收回边上，**位置留着** | 拖出来的窗落在 (299, 547)（实测），摞里其余八扇仍在，九扇的 id 一模一样 |
| 三 · **快捷键** | 指针**离开边缘**（x = 1000），按 `W`。再按一次收起 | `dock=0`，`open=[find]`——与边缘那一条**逐字相同** |

自检原文：

```
ok  边缘路：dock=0 open=[find]
ok  静置时是半开的窗（clip-path inset(0px calc(100% - 76px) calc(100% - 24px) 0px)）
ok  拖拽路：窗落在 (299, 547)，记在 localStorage
ok  快捷键路：dock=0
ok  边缘与快捷键唤出的是同一个面：open=[find] vs [find]
ok  两条路的窗摞都是那九扇（9）· 拖拽路也是同一摞窗
```

**同框的还有一个「雾」**：工具层打开时，左边缘漫出一层很淡的 `--w-glass` 渐变（`.t-scrim`），让工具层读成更前的一层玻璃，后面的内容退后。这是对「窗多了会盖住内容」这条风险的正面回答的一半（另一半是**默认一次只开一扇**，Shift 点窗沿才并排开）。

## 5 · 这个方案成不成立、哪里最弱

**我认为成立，而且它是四个里落地最直接的一个。** 理由：

1. **「前层」在这个站里的字面意思本来就是「更薄的一片玻璃」。** 内容的窗已经定下了一整套语言（`--w-glass` / `--w-edge` / `--w-sheen`、空心小圈 + 发丝的标题栏、三种夜色），工具层只是把同一套语言**再薄一档**——不需要另造一种材质。这是四案里唯一一个「材料本身就说清了它为什么在前层」的。
2. **动词与物件是同一件事。** 窗的「开」就是窗的「开」，不用解释：收起来是窗沿，打开是窗。悬停（靠近边缘漫出来）与展开（那一扇自己长开）是同一个动作的两段，不是两个决定。
3. **失焦档位与飞行过渡已经有人趟过**（`wander` 的卡面画法、`faces.js` 的三档失焦、投影与磨砂只在清楚那一档给），接过去成本最低。
4. **十二件工具挤进九扇小窗之后仍然都读得清**——见第 4 节的表；窗里最窄的一扇（`where`，158px）放三段、每段一行，也不挤。

### 最弱在哪

1. **最不新——这是它最大的问题。** `design/p5-floatwin.html` 与 `scene-floatwin-notes.md` 已经把「窗即入口」的 OS 桌面语义探过一遍（四扇小窗挂在 14° 线上、编号 · 窗名 · 命题徽标 · 最近条目）。这一案与它的区别只有两条，都得靠人眼确认够不够：① 浮窗那四扇是**内容的入口**（点进去是版块），这一案的九扇是**工具**（打开是控件）；② 浮窗是「挂在线上」，这一案是「贴在左边缘、半开着、从边上漫出来」，并且**刻意比内容的窗薄一档**。如果站长看完觉得「就是重做了一遍 p5-floatwin」，这一案就该让位。
2. **薄一档在极亮的底上几乎看不见玻璃。** NEXUS 那一屏的天光中段接近 `#fef7f5`，工具的窗（alpha .34 的白玻璃）压上去只剩字与一条发丝边，玻璃本身消失了（见 `10-gate`）。**这不是 bug，是「薄一档」的代价**——但它是这一案的真上限：底色越亮，那层玻璃越不存在。我把工具窗的边从 0.15 提到 0.18、投影从 16px 提到 18px 补了一点，再往上加就会伤到「薄一档」本身。
3. **小窗里的可读性到顶了。** 目录窗 236px 宽、条目 11.5px；`where` 158px 宽放三段，每段一行。再塞进去一件工具就得再加一扇窗，而窗一多就会盖内容（见下）。
4. **窗多了会盖住内容。** 这是三个风险里我处理得最实的一个，但只是缓解不是解决：默认**一次只开一扇**（同类的控件仍然分得开，因为九扇窗沿一直在）、打开时左边缘漫出一层雾、指针离开边缘就自动收回。但如果你 Shift 点开三四扇（`?multi=1`），左边那 260px 的内容确实被盖住——`40-CMP` 那张对照帧就是这个状态。
5. **工具层自己的夜色是整层一套，不随底换。** 在检索页里工具层默认取随笔那一栏的浅梦色（点场景 / 按 `1 2 3` 才换），拖出来的窗飘到深色的瞬间 / 项目栏上时不会自己转墨——`wander` 的 `[data-ink]` 做到了，这一案没做。深底上浅玻璃的对比度仍然够（自检里 4.6–9.2），只是观感上会「亮一块」。

## 6 · 发现了但没处理的问题、需要人眼确认的地方

### 处理掉的（留在记录里）

1. **`--w-faint` 在薄玻璃上够不到 3:1**：浅底上它只有 **2.22–2.87**（见上表），因为薄玻璃后面的有效底很亮。所以凡是有字的地方**一律退到 `--w-soft`**（浅底 4.6–5.4，深底 9+），`--w-faint` 只留给发丝与装饰点。内容的窗上也一样处理（0.62 的底也救不了 faint）。这条是「薄一档」的直接后果，值得写进正式规范。
2. **`--w-faint` 只用在 `--g` 这种非文字处**，没有例外。
3. **拖出来的窗落错地方**（真 bug，已修）：那一摞 `.t-shelf` 上有 `transform: translateY(-50%)`，它成了 `position: fixed` 子元素的**包含块**，于是 `left: 299px` 是相对那一摞的盒子而不是视口——窗会跑到屏幕外。现在拖出来的窗住进一个没有 transform 的 `.t-floats` 层（`22-path-drag-1-moved` 已对上）。
4. **`backdrop-filter` 与裁剪**（`wander` NOTES 第 1 条的同一个坑）：半开那一下的 `clip-path` 加在窗自己身上，实测磨砂照旧（`21-path-edge-2-opened` 里能看见后面卡片的字被 7px 模糊），所以半开态可以放心裁。
5. **窄屏的抽屉会让内容被压**：390 宽下如果照桌面那样把小窗漂在内容上，正文会被盖住。现在窄屏**退成底边一条抽屉**（九条窗沿横排两行、66px 一格），开窗时抽屉长高、**内容整体让开那一条**（`.t-space { bottom: var(--sheet) }`，抽屉量完高度再让）。自检里三条窄屏帧都断言了「内容没有压在抽屉下面」与「没有窗越出视口」。另外抽屉自己**不带 backdrop-filter**——带了就会变成 fixed 子元素的包含块，拖窗又落错地方。
6. **浏览器默认按钮皮**漏进了「去处」窗（回主页 / 去门口带了一圈默认边框），已按 `.t-win button { appearance: none; border: 0 }` 统一脱掉。
7. **`?verb=` 与 `prefers-reduced-motion`**：RM 下所有过渡与弦的动画都退成静态，打开就是打开（自检 `60-reduced-motion`）。

### 没处理、要知道的

1. **NEXUS 那一屏的玻璃几乎看不见**（第 5 节第 2 条）。要在那里立住「薄一档」，可能得让工具层在天光那一屏**换一种存在方式**（比如只用发丝与字、不要那层玻璃）——这一案没做，因为那已经不是「薄玻璃窗」了。
2. **工具层不随底换墨**（第 5 节第 5 条）。
3. **`?many=1` 时目录窗只列前 12 条**、检索只筛当前语境里已经渲染出来的窗（检索页的三栏都渲染了，主页只渲染三扇内容窗）。真站上检索要跨全部内容，这一案只证了 UI 成立。
4. **没有无脚本兜底的工具层**（这一轮不要求），`index.html` 里只留了一句名录与归处 / 门 / 出口三条真链接。
5. **真机手感**：截图只能看帧。指针进 / 出 170px 那条线时，工具层漫出与收回的**迟滞**、拖拽的跟手程度、`clip-path` 在低端机上的帧率，都只能上手。软件渲染下的性能数字不代表真机。
6. **`.t-scrim` 的浓度**（左边缘那层雾）是纯观感，没有量化的依据。
