内角半径的算法在 `src.js` 的 `notchRadius()`：六张风筝都含原点，并集是关于原点的星形域，
所以一条射线只出射一次，`R(θ)` 良定义；在 0°–60° 里扫 `R(θ)` 取最小值（六重对称）。

现役那档（`halfWidth = 1.9`，即 0.119）：内角 **3.035 单位 / 200px 上 15.18px**。

### 三条读数的方向

1. **内角随粗细单调变远。** 支越粗，内角被推得越靠外：0.08 档内角还缩在星心 2.19 处，
   是一道深 V；0.62 档已推到 9.12，只剩一道浅坑。
   **所以在这族几何里，内角变大 = 六支并得越紧。** 这与 star-solid 那份
   「内角至少 2.8px 才读得出」的用法方向相反 —— 那里内角是「别糊在一起」的下限，
   这里它同时是「别并成一块」的上限。两个方向要一起看才有效。
2. **真正单调的是 `a6`**（极径剖面的六重谐波幅度 / 平均半径）：0.672 → 0.138。
   它一路降，没有回头，是这三列里最能代表「还像不像六芒星」的一个。
3. **剪影填充率**（面积 ÷ 半径 13.064 的正圆）：0.160 → 0.644。
   过 0.5 之后（0.40 档起），六支的边界就再也说不清在哪了。

## 二、与 star-solid/notes.md 的一处不一致（没解决）

那份记：**现役内角 = 2.8135 单位，200px 上 14.07px**（依据是它的 `2.8135 × 5 = 14.07`）。
我按它的几何（同样六张风筝、同样 `halfWidth 1.9 / notch 1.4`）重算，得 **3.0354 单位 / 15.18px**，
差 **7.9%**。

我试过几种量法想复现 2.8135，**都对不上**：

- 相邻两风筝的四对边求交，全部不相交（说明「内角」不在边的交点上，而在 `D` 顶点自己那里）；
- 六个 `D` 顶点半径恒为 `notch = 1.4`，不是 2.8135；
- 全部风筝两两边的交点里，半径最接近的几档是 1.134 / 1.230 / 1.301 / 1.900 / 2.024 / 3.035，没有 2.8135。

我的猜测（**未验证**）是那份把某个「点到边」的距离当成了到内角的距离，
但这是猜的。**结论：以 3.0354 / 15.18px 为准；2.8135 这个数目前复现不出来。**
它的量级与用法（2.8px 是下限）不受影响 —— 3.035 与 14.07、15.18 都指向同一档判断。

## 三、中心：变粗之后发生了什么

400px 那颗星的中心一直没被细看过。`index.html` 第二段把中心 **7.5 单位见方**那块
放大 **4.27 倍**、并去掉中心圆，单独看。

**变粗修好了中心的糊，但也只修到 0.32 为止。**

- **0.119（现役）**：中心是六张极窄的风筝在原点附近交叠，每一张都只剩一条边，
  叠出来是一小团带六道细裂纹的深色块。**「交叉的碎条」这个描述成立** ——
  中心那圈暗不是形状，是六条边互相压出来的。
- **0.20**：六张风筝各自有了宽度，中心变成一片实心的六边形，六道裂纹变成六道
  **面的折边**。这是第一次中心不再是「好几条线打架」，而是一块料。
- **0.26**：同一块料更厚，折边更短、更靠外。中心读成一颗有六个面的球冠。
- **0.32**：折边几乎贴到轮廓上，中心那块实心六边形开始吃掉整个星心，
  内角已离星心 6.10 单位（星尖 13.06），只剩 46%。

顺带一个数：**中心那一点永远是六层全叠上的**（六张风筝都含原点），合成不透明度 0.998。
所以「中心为什么那么黑」不是深度算错了，是六层各 0.486/0.774 叠出来的必然结果。
这也是为什么**加粗对中心暗度的改善有限** —— 变的是形状（碎条 → 面），不是深浅。

## 四、支尾回伸：只改明暗，不改剪影（与简报预期不符）

简报假定支尾（`notch = 1.4`，越过星心往回伸）是「唯一往星心里填东西的一笔」，
并要我把它在 1.0 / 1.4 / 2.0 之间扫一遍。扫完了，**结论与简报相反**：

| 支尾 | 内角半径 | 剪影面积 | 中心合成明暗的最大差 | 差 > 0.02 的像素 |
| --- | --- | --- | --- | --- |
| 0 | 5.3624 | 不变 | 0.058 | 2172 |
| 0.7 | 5.3624 | 不变 | 0.058 | 708 |
| 1.0 | 5.3624 | 不变 | 0.057 | 354 |
| **1.4（现役）** | **5.3624** | — | — | — |
| 2.0 | 5.3624 | 不变 | 0.058 | 422 |
| 3.0 | 5.3624 | 不变 | 0.058 | 1354 |
| 4.0 | 5.3624 | 不变 | 0.058 | 2842 |

- **剪影完全不变**：`notch` 从 0 拉到 6.0，内角半径一个数都不变（0.26 档恒为 5.3624），面积也不变。
- **中心明暗会变，但很轻**：最大 0.058（约 6%），而且**不是单调的** ——
  1.4 恰好是「差最少」的那一档（0.7 / 1.0 比它差，2.0 / 3.0 / 4.0 也比它差）。
  这是叠加次序的问题：支尾长短改的是六张风筝谁压在谁上面，不是多盖几层。
- 逐像素比对 `.shots/r-detail-tail.png`：0 / 2.0 / 4.0 三档与 1.4 的差别只有
  max 9/255、几十到几百个像素超阈值；**只有 0.7 档差得多**（max 113，2033 像素超阈值），
  因为 `notch = 0.7` 时风筝的 `D` 顶点挪到了中心圆（1.7 单位）的里面，露了出来。

**结论：** `notch` 是「中心明暗的微调」，不是「中心填充的来源」。填满中心的是 `halfWidth` ——
风筝从原点往两侧各张开 `halfWidth`，**加粗才是唯一起作用的旋钮**。
现役的 1.4 恰好落在差异最小的位置，可以留着，但不必再调它。

我把这段留在页面上当反例，没有为了让图好看而改成别的参数。

## 五、尺寸

`halfWidth/r = 0.26` 与现役 0.119 在同一页对照（`index.html` 第三段）：

| 画布 | 0.26 的内角 | 现役 0.119 的内角 |
| --- | --- | --- |
| 48 px | 6.43 px | 3.64 px |
| 96 px | 12.87 px | 7.28 px |
| 200 px | 26.81 px | 15.18 px |

- 工具栏那颗实际是 **40px 画布（星径 26.1px）**。按比例，0.119 在 40px 上内角只有 **3.04px**，
  正好压在 star-solid 判定的 2.8px 线上；换到 0.26 是 **5.36px**，余量快翻倍。
- 但**更大的内角不等于更清楚**：48px 下 0.26 那档的六个内角已经很浅（内角/支尖 0.41），
  六支的边界靠的是「六个凸出」而不是「六道深 V」。
  缩小之后先丢的是**支与支的分离**，不是支本身。

## 六、没做到的 / 与预期不符的

1. **支尾回伸对剪影无效**（第四节）。这是这一轮最重要的一条：它只改中心约 6% 的明暗，
   不改轮廓。简报把三档（1.0 / 1.4 / 2.0）当成三种不同的形，实际不是。
   而且 1.4 恰好是差异**最小**的那一档，不是「填得最多」的那一档。
2. **内角半径不是单调的「越大越好」**。它与 star-solid 的用法方向相反，
   两份文档放一起看会互相打架。我保留两种读法，没有强行统一。
3. **2.8135 这个数复现不出来**（第二节）。差 7.9%，我没能定位那份是怎么量的。
4. **只验了 `flat` 这一种材质**。简报要求「六个尖就是现在这样（平风筝，深度靠透明度）」，
   照做了；但平风筝在 200px 上「六片各是各的平三角」这个老问题，
   **加粗并没有解决** —— 0.26 档在 200px 上仍然能看出六片是六张贴片，
   只是每片更宽了。真正的分界靠的是 star-solid 的 `ridge`（沿脊线折），那不在这一轴的范围内。
5. **没有做「粗细随尺寸变」的组合**。48px 与 200px 是否该用同一个 0.26，这轮没答。
   从内角/支尖比看，48px 也许该更细一点（0.20–0.22），但那是另一条轴。
6. **`a6` 与视觉判断没有正式对齐**。0.62 档 `a6 = 0.138` 已经很低，
   但肉眼看它更像「六边形」而不是「圆」—— 说明六重谐波不是判断「读不读得出六支」的唯一量。
   我没有再找一个更好的指标。
7. **只验了 Chrome**。字体、抗锯齿、SVG 渲染都没在其他浏览器上复查。
8. **截图期间我把汉字字形当成了缺字**：一度以为「凹」「口」显示成了方框
   （它们本来就是方框/缺口状的字形），为此写了 8 个临时试验页去查字体栈与 DPR。
   查完确认字体正常，试验页已全部删除。**为减少歧义，页面上的「凹口」已统一改成「内角」。**
   这一条写在这里是为了提醒：截图要看清了再说。
9. **一处过程事故**：用 PowerShell 批量替换术语时，`-replace` 的 `|` 被当成了正则分隔符，
   把 `notes.md` 写坏过一次（第 28–49 行变成一长串重复行）。已整份重写修复，
   现在这份是干净的。**批量改写正文应该用 write 整份重写，不要用正则逐条替换。**
