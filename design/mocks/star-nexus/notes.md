## 2. 非凸：换了什么

NEXUS 的外壳是 24 胞体的切面，**永远凸**，所以它一个 `exitT()` 扫 24 个半空间就得到出射面，
每次体内全反射再加一次同样的扫描。六尖星不是凸的（六支之间是凹口，凹口是深进去的）。

### 做法：凸体并集，精确解，不是 SDF 步进

六支各沿轴切成 `seg` 段（默认 **2**），每一段是一个**凸棱台**：`NOCT = 8` 张侧面 +
2 个端面 = 10 个半空间，最多 `MAXP = 24` 块。整颗星就是这 24 个凸块的并集。

- **逐块**：`pieceAt(P,T,k)` 从 10 个半空间解出 `[ta, tb]`（凸体 ⇒ 唯一区间，无歧义）。
- **合并**：`exitUnion()` 取 **所有「包含 P」的块里 `tb` 的最大值**。
  这一条是整个做法的支点，值得说清为什么它是**精确**的：块是凸的，`P` 在块内时，
  `P` 之后该块内的可见段就是 `[0, tb]` 连续的一段；于是并集的出射时刻
  = 所有含 `P` 的块的 `tb` 的上确界。六支在星心互插的那一团因此自动解掉——
  光线从 A 支穿进 B 支体里时，A 的 `tb` 被 B 的 `tb` 盖过，不在那儿折。
  那儿本来也没有面，所以「不折」是对的。
- **出射面**：取那一块的 `nb`，接下去的全反射/色散全走 NEXUS 的原逻辑。
- **剔块**：先用包围球把「`P` 不在其中」的块整块跳掉，真吃 10 个半空间的通常只有一两块。

半空间表 240 个 `vec4` 塞不进 uniform 数组（ES3 只保证 224 个 fragment `vec4`），
所以放进一张 `RGBA32F` 纹理（宽 10、高 24），`texelFetch` 取，不插值。

### 踩过的三个坑（都写进代码注释了）

1. **半空间的 `d` 忘了跟着视图矩阵的平移走。** 视变换是 `x_v = R·x_w + t`，
   `n_w·p ≤ d` 搬过去是 `n_v·p_v ≤ d + n_v·t`。漏了 `+ n_v·t`，整副半空间停在视空间原点，
   而网格在 `z ≈ −6`，两者对不上 → `exitUnion` **一路返回「找不到出射」**，
   画面是一颗没有折射的、折纸一样的平板星。**这是第一轮最要紧的一个 bug。**
   同理 `uCoreC` 也必须走完整的点到视变换，不能只转不平移。
2. **支尖那一块被悄悄丢掉了。** `f(1) = 0`，最后一段的末端环退化成一点，端面平面 `planeOf`
   返回 `null`，于是 `pls.length !== NPPL` → `continue`；可它的三角形**已经推进去了**。
   块号一断，着色器拿块号去查半空间就查到隔壁，`L` 恒为 0、`e` 恒为 0（全星都在「棱」上）。
   修法：末端半宽钳一个极小非零值（`w·2e-4`，画面上是半点大小），十张面齐了，
   而且改成**先验面齐了再推三角形**，块号永远连续。
3. **出射容差太小。** `ta > 1e-3` 太紧：并集边界上 `P` 恰好贴着两张面，浮点抖动会让
   「这一块含 P」判假，出射时有时无，画面上是一道道断掉的黑线。放到 `4e-3`。

### 与 NEXUS 的两处**有意**的不同

**① 正交投影，不是透视。** 六个支尖在体对角视角下等距、相邻 60°，这是三维里的事实；
但透视会把它们拆成近三远三。实测（`.geo.mjs` 同款投影算式，`dist = 4.3`、
NEXUS 的 `fov = 0.62`）：

```
-z r=0.5226 30°   +y r=0.6847 90°   -x r=0.5226 150°
+z r=0.6847 210°  -y r=0.5226 270°  +x r=0.6847 330°
```

半径比 `0.685 : 0.523`，差 **31%** —— 那不是六芒星。NEXUS 用透视没问题，因为它那团切面
很紧凑、六个方向的深度差很小；这一页要判的恰恰是「六支相不相等」，所以改用正交
（`HALF = 1.18`，滚轮改的是这个半高）。**这是有意的偏离，不是抄漏。**

**② `env()` 加一道很淡的蓝紫染色 `uTint = (0.985, 0.993, 1.045)`。**
实测（`.cmp.py`，同一张底、同一套统计，只比星内像素）：

| | 星内平均色 | B − R | 亮度 5% / 中位 / 95% |
|---|---|---|---|
| NEXUS `wake.webp` | `rgb(206,200,216)` | **+10** | 160 / 215 / 251 |
| 这颗星（未调） | `rgb(210,202,206)` | **−4** | 158 / 212 / 255 |

差的不是明度（分位几乎重合），是**色相**：整颗偏暖。原因不在 `env()`（它逐字抄的），
在几何：那枚切面是紧凑的凸体，光穿过它多半打到地平亮带与丁香天顶；六支星的尖又细又长，
视线在尖上几乎与面平行，出射光线大半落进下半球（`low = vec3(0.78,0.745,0.80)`，比上半球暖）。
染色按上表对齐，**`env()` 的每一项都没动**。扫过的档位见本文件 §5。

## 3. 形状：四个旋钮

都作用在几何上，材质不动 —— 所以 `形状` 那一节能直接判「形对不对」，不只是「材质好不好」。

| 旋钮 | 范围 | 说明 |
|---|---|---|
| **粗细** `w` | 0.16 – 0.40 | 根部截面的大小（菱形半对角，面积 `2w²`） |
| **弧线** `prof` | 直 / 凹 / 深凹 / 凸 | 沿轴的母线，`f(0)=1、f(1)=0`，按段采成折线 —— 所以「凸」母线依然是凸棱台的并集，精确性不丢 |
| **截面倒角** `bev` | 0.05 – 0.92 | 菱形四个角倒掉的量；0.08 近乎四张面，0.70 近圆。截面在「交换 u 与 v」下不变，这是整颗星对立方群逐点不变、剪影是**正**六芒星的前提 |
| **平滑** `round` | 0 – 0.08 | 圆角棱的宽度；0 是硬棱（棱上那道细光最利） |

**为什么默认 `seg = 2` 而不是 4。** 段多了每支上就多一圈切出来的棱，光在那一圈上折两次，
画面上是一串小台阶 —— 四段的版本读起来像玻璃刺猬。NEXUS 那枚切面总共二十来张脸，
光靠这么几张就把深度说清楚了。`.geo.mjs` 的数：

```
pieces 24  tris 672      ① 半空间朝外：块心到各面的距离都 > 0
② 入射后找不到出射的方向数：0 / 27      ④ 支尖最远点 r = 1.0000
③ 绕 x/y/z 各 90°、绕 (1,1,1) 120°：不在集合里的顶点 0 / 0 / 0 / 0
```

## 4. 醒梦

`reality.ts` 写 `documentElement` 的 `--reality-mix`（0 梦 · 1 醒）。
这一页**没有 import `../scripts/reality.ts`**（那个模块从 `/src/scripts/` 取，mock 这边解析不到），
改用 **`MutationObserver` 盯 `documentElement` 的 `style` 属性** + 听它派的 `xm:reality` 事件，
读 `--reality-mix` 后翻成 `uDream = 1 − mix`，再在 **1.2 s** 里逐帧逼近（与 `nexus-slice.ts`
的平滑时长同一个数），到站即停。

`醒梦` 那一节的两个按钮写的就是页面上的 `--reality-mix` 本身，不是这一页自己的开关 ——
所以「跟着走」是能被亲眼验的：按「梦面」，上面那颗主星也跟着换调。

实测（`.shots/r7-06-wake-dream.png`，同一姿态、写死 1.000 与 0.000 并排）：
**8.0% 的像素差 > 10，最大差 610**，平均位移 `R−0.4 G−0.1 B+0.0`。
差异比醒目的部分在尖部与中心那团光核上（`uCore` 与 `k` 都随 `uDream` 走），不在整体明度上
—— 这是对的：NEXUS 的醒梦也不是整体调亮调暗，是吸收色从丁香换成偏粉、天顶换一档。

## 5. 代价

**块计时**：连着画 40 帧、块末同步一次、除以 40，跑 5 块取中位。

> **同步的写法是关键。** 用 `gl.finish()` **量不出东西**：headless + ANGLE/D3D11 在没有待查对象时
> 它差不多是空转，给出 **0.032 ms** —— 一万四千个像素、每个还要跑 24 块凸体 × 4 段，
> 不可能三十微秒画完。换成 `readPixels`（一定要等批次落地才有像素可回）当栅栏，读数落到
> **1.195 ms**，五块分别 `1.230 / 1.275 / 1.050 / 1.113 / 1.195`。
> 这一条值得记下来：**这个仓库里凡是报「零点零几毫秒」的块计时，先怀疑栅栏。**

| 项 | 值 |
|---|---|
| 中位 | **1.195 ms/帧** |
| 位图 | `820×387`（§`晶体` 那一格就是整张画布，`dpr = 0.712`） |
| 凸体 / 三角 | 24 块 / 672 |
| 页面总量 | `23` 格 → **4 张画布**（`4` 个 WebGL2 上下文）：1 + 1 + 19 + 2 格 |

`23` 格摊在 `4` 张画布上，是因为五节各自一块 `.stage`：主星一格、对照一格、
`形状` 那十九格共享一块、`醒梦` 两格共享一块。每块画布各自 `ResizeObserver`，
只在尺寸真的变了才重画。`Chrome 每页约 16 个 WebGL2 上下文`是这里必须摊的原因 ——
一格子一个上下文，`形状` 那一节自己就超了。

对照 `nexus-slice.ts` 实测的 ~3 ms/帧 @1040px：这一页更便宜，因为面积更小（820×387 对 1040²）、
而且包围球剔块之后每像素通常只吃一两块凸体。

**上限（都写在页面的 `代价` 表里）**：

| 上限 | 值 | 为什么 |
|---|---|---|
| 单格位图长边 | **820 px** | NEXUS 是 900；这一页要摊二十几格，再高只是多烧填充 |
| 整张画布长边 | 1500 px | 让长页面上的格子一起塞进一张画布（Chrome 每页只给 16 个 WebGL2 上下文） |
| 凸体数 / 每支段数 | 24 / 4 | 六支各分 `seg` 段凸棱台 |
| 体内段数 | 4 | 入射 + 至多三次全反射，与 `nexus-slice.ts` 相同 |

**回退**：`failIfMajorPerformanceCaveat: true`；按渲染器名再挡一道
（`/swiftshader|llvmpipe|softpipe|software|basic render/i`）；拿不到 WebGL2、着色器编不过、
链接失败 → `data-gl="off"`，停在静帧上，**一个 rAF 都不排**。掉了 GPU 上下文不重建。
`prefers-reduced-motion` → 只画正位一张，不播翻动，**一个 rAF 都不排**。

## 6. 定格：零帧的取证

翻一次是 **12 格离散姿态**（每格 `setTimeout` 105 ms 后一跳，格间**不补间**；最后一格多停 3 拍），
到站 `cancelAnimationFrame` + `clearTimeout`，然后什么都不排。

`.shot.cjs` 里的实测（`r7-report.json`）：

```json
flipRun: 翻一次实际画了 13 帧（12 格 + 落回正位那 1 帧）
flipRun.pose:          { az: 45, el: 35.264 }        ← 落回体对角正位
flipRun.proof (2001ms): before 36 → after 36   Δ = 0 帧
                        raf 0 · timer 0 · busy false · mixRaf 0
```

`prefers-reduced-motion: reduce`（CDP `Emulation.setEmulatedMedia`）：

```json
rmRun.start:  { started: false, reason: "reduced-motion" }
rmRun.proof:  before 8 → after 8   Δ = 0 帧 · raf 0 · timer 0
```

翻动**之后**再拖一下、滚一下（`.orbit.cjs`，真鼠标事件走 CDP），确认松手之后又会停：
`az 45 → 141.8`、`el 35.264 → −0.736`、`zoom 1 → 0.736`，随后静置 1508 ms **Δ 0 帧**。

## 7. 与 NEXUS 对得上吗

**对上了。** 证据是 `.shots/r7-11-pair.png`（按剪影等大裁齐、同一张 `#f0f3f6` 底）。
数值见 §0 与 §2②。

读感上一致的地方：淡丁香的底、近白的地平亮带、右上一道软边、内部那团近白的微温、
棱上一道利而不断的高光、以及**连续**的明暗过渡（这一条是反面判据：
量化成四档会让它读成折纸，这一版没有任何量化）。

**仍然不同的是这几处，都是几何带来的、不是材质带来的：**

- **脸的大小差一档。** NEXUS 那枚切面有二十四张脸，每张占画幅的比例都比较大；
  六尖星摊开成六支细长的尖，同一块切面在尖上被拉成很窄的一条。
  所以细看时尖部那些面比 NEXUS 的碎。这是「六尖」这个形自己决定的 ——
  把 `seg` 降到 2 已经把碎的程度压下去一轮，再压就只能把尖做钝（`弧线` 里的「凸」母线）。
- **凹口那里没有 NEXUS 的对应物。** 六支交汇处是凹棱，`edgeDist()` 只数**这一块自己的
  八张侧面**（不跨块）。跨块的凹棱如果也把法线朝对面弯，会在这个站的语言里画出一道不该有的亮线 ——
  所以让它保持一道干净的交线。凹口因此比 NEXUS 的任何一处「利」一点。
- **没有背景剪影。** NEXUS 那一页晶体背后有脑电线，`env()` 里的 `uLine` 会把那条线折射出来；
  这一页没有那条线，所以 `uLine` 恒为 0，那一段代码没搬。

## 8. 没做到的 / 与预期不符的

1. **透视下的六芒星是假的，这一点改了你的规格。** 你写「rest pose 是 yaw 45° / pitch 35.264°，
   961 格里唯一让六支等半径投影成真六芒星的一格」。姿态是对的，但**在透视投影下它投不出
   等半径的六芒星**（§2①，31% 的差）。我把投影换成了正交。如果这一页的意义是「在 NEXUS
   那套相机下看」，那就该留透视 —— 但那时候「六支等长」在画面上不成立。这是一个取舍，
   **需要你拍板**：现在看来正交更像「一个模型」，但如果你要的是「和 NEXUS 同一个镜头」，
   我把 `persp()` 换回来就是一行。
2. **`seg` 从 4 降到 2 是我改的默认值。** 四段的版本在你给的「凸体并集」框架里完全正确，
   但画面上每支多出三圈切出来的棱，读成玻璃刺猬。降到 2 段之后面大、深度清楚。
   如果你要更贴合的母线（「深凹」在 2 段时其实只折一次），段数该往上调，
   代价是画面更碎、每像素多轮几块。
3. **`uTint` 是一处「为了让数对上而加的东西」**，不是 NEXUS 的代码。我知道这类补偿
   容易变成掩盖问题；所以它不带任何明度项（三个数乘起来 ≈ 1.02，只动色相），
   而且上面把「为什么几何导致偏暖」写清楚了。**如果你更希望 env() 一字不改，
   就把 `uTint` 设成 (1,1,1)**，那时星内平均会回到 `rgb(210,202,206)`，比 NEXUS 暖一圈。
4. **`圆角棱` 只做块内的棱。** 跨块的凹棱没做（理由见 §7）。严格说「圆角棱」在凹口是不完整的
    —— 但凹棱如果圆了，六支交汇处会出现一条不该有的亮带。
5. **没有做「长出来 / 进门」这类过渡。** NEXUS 的 `grow`/`enter` 是给 about 页退场用的，
   这一页没有那个语境，`uEnter` 相关的几行（光核漫开、色散放大）没有搬。
6. **帧率没在真机上测。** 1.195 ms 是 headless + ANGLE/D3D11 + Radeon 610M 上的块计时。
   真浏览器里 `readPixels` 会把管线打断，实际帧时间不等于这个数；这个数只能用来比
   「同一页上不同几何的相对代价」。
